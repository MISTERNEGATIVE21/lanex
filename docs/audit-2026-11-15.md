# LanEx full audit and fix plan (2026-11-15)

Audit of `main` at b3664e0 (v1.0.0), ahead of the public launch. It covers the whole
product: install, first run, Setup and config, RTL IDE, running a flow, the fix loop,
Runs and sweeps, Analytics and Compare, Verify, Layout, Cells and macros, Tools and
PDKs, the app shell, the backend and the code's health. No code was changed.

How to read the evidence tags on each finding:

- **[L]** seen live on a private test server with real runs (screenshots in the session scratchpad)
- **[C]** I read the cited code myself and confirm it
- **[A]** found by one of the eight Opus audit agents with a file:line; plausible, not re-checked by me
- **[?]** needs a test before anyone builds on it

Read with `PRODUCT.md`, `docs/workflow-spec.md` and `docs/polish-plan-2026-10-28.md`.

---

## 1. The verdict

The app looks finished and, on the happy path, it is good. A Blinky run from the
wizard to a GDS took 37 s and the Flow page during it is the best screen in the
product. The visual system is consistent, the fix loop is a real idea, YAML configs
round-trip safely, the Windows installer's preflight and hash pinning are careful,
and the command palette, Verify's honesty and the Tools page all hold up.

Correction after the owner's review (same day): the first draft said the look was not
the problem. That was wrong. Each component is tidy, but the screens as a whole are
overloaded, and the owner rates the UI as the product's weakest part. Section 10
holds the UI findings and the redesign direction; the UI redesign runs as its own
piece of work, owned by Fable, and the feature phases build into the surfaces it
defines.

Underneath the UI there are nine structural problems, and almost every individual
finding in sections 3 to 7 is a symptom of one of them:

1. **Data-safety holes.** A handful of paths can delete or overwrite the user's work
   (section 3). These gate the launch.
2. **Two settings models that leak into each other.** Some controls write the config
   file, "All settings" is an invisible per-run override layer. The override layer
   shows LibreLane defaults instead of the project's values, survives a project
   switch, rides along on every sweep point, and is where one-click fixes are saved
   by default. Users cannot tell which one they are editing, and the app's own copy
   gets it wrong.
3. **One run at a time, held in memory.** No queue, sweeps are strictly serial, a
   server restart loses the sweep and silently drops live events, nothing recovers an
   interrupted run, nothing keeps the PC awake. This is the root of the sweep pain.
4. **LibreLane's real surface is not reachable.** Every run is the Classic flow (a
   config's `meta.flow` is ignored), `--from/--to/--skip/--only` are not exposed,
   `pdk::` scoped values cannot be edited (so editing the clock on LibreLane's own
   SPM example does nothing), there is no multi-config support and no config
   validation before a run.
5. **The app repeats itself.** The same "Clean" verdict card appears on Flow, in the
   Runs row, on Analytics and on Verify. There are three PDK pickers, two baselines,
   two cell taxonomies, six verdict vocabularies, and a marketing hero that stays on
   Setup above the open project on every visit.
6. **Teaching stops where it matters.** Only four tool error codes are explained.
   Nothing validates the config before a 5 to 60 minute run. The glossary is never
   inline. Layout never says what the user is looking at. Example testbenches check
   nothing.
7. **Pro analysis is thin.** Sweeps have no results table, no chart by swept value,
   no resume. Compare has no deltas. Timing paths are not in Verify or Layout. No
   warnings triage, no report export, no Settings page, no update check.
8. **Install supply chain is uneven.** Windows is pinned and hash-checked. The Unix
   one-liner installs `main`, in-app installs are unpinned (one pipes
   get.docker.com to root), nothing tells a user a new version exists, and after an
   upgrade runs silently use the old image with the new LibreLane.
9. **Code health.** `routes.py` is 4,829 lines with 141 handlers routed by path only;
   632 broad `except Exception`; four overlay systems; seven HTML escapers; about
   138 dead CSS classes; a 2,000-line unreachable landing page.

The plan in section 8 fixes these in that order. Section 3 is the launch gate.

## 4. Findings by area

Only the findings that matter; each agent's full list (40 to 80 items per area) is in
this session's transcript and can be re-run.

### 4.1 Install, update, uninstall

Good: Windows wizard order, preflight (memory, disk, virtualization with a
reboot-to-firmware offer), honest progress with no fake ETA, resume after restart,
log path on every failure, hash pinning for everything Setup downloads, TLS never
weakened.

- **No update check anywhere** (app, image, PDKs). Users never learn of fixes. Add an announced, opt-out GitHub releases check with a banner and "what's new". [C]
- **Unsigned EXE**: SmartScreen blocks beginners. Azure Trusted Signing; until then, screenshots on the download page. [A]
- **Corporate and university networks**: the Windows proxy is not passed to apt or dockerd, and no corporate CA is imported into the distro, so the pre-check passes and the install fails later (`lanex.iss:868`, `provision.sh:103`). [A]
- **WSL memory**: WSL takes half the RAM; the only guidance is a hint to hand-edit `.wslconfig` (`runresources.py:441`). Offer it on the Configure page and in Tools. [A]
- **Jargon failures**: "did not pass the structured Windows/WSL preflight: not-enough-memory", "bind its exact Windows registration identity", raw curl exit codes, "Please report it" with no address (`lanex.iss:3257,3505,3311,2747,2991`). [A]
- Welcome says "a few GB" (Recommended needs 22.5 GB); no time estimate (measured about 18 min); no drive choice. [A]
- First launch: up to 90 s with feedback only in a tray tooltip; a missing distro sends the user to GitHub instead of the installed Repair. [A]
- Two different "project files" places (tray opens the Linux home, Start menu opens `LanEx-Projects`). [A]
- Unix: no uninstaller; a user without sudo cannot install even Minimal; `ln -sf` clobbers an existing `/usr/local/bin/lanex`; rc PATH line appended on every re-run; rootless Podman never checked; GDS3D on Apple Silicon needs Rosetta that is never installed; viewers on Linux run as root and leave root-owned files in the project (`container_tools.py:459`). [A]
- Tools page: Remove reports success while the package is still installed under pipx; PDK remove is per family (removing sky130A removes sky130B); a half-unpacked PDK reads as ready; the PDK folder setting is lost on restart; no install log on disk; a second Install click within a second gets a 429 and the button sticks on "Installing…"; image pull has no retry. [A]
- CI never runs `install.sh`'s real paths, macOS, or a Windows VM install. [A]
- No CLI subcommands (`lanex doctor`, `lanex pdk …`, `lanex --uninstall`). [A]

- A blank project with a top name like "my chip" or "1top" is created broken (`scaffold.py:155` skips the rename silently). The wizard accepts a clock of 0, an uninstalled PDK, and a parent path with spaces. Running the guide twice gives the raw "destination directory is not empty". [A]
- The PDK pick is not saved for configs without a `PDK` key (SPM, most imported projects): it snaps back to sky130A on reopen (`setup.js:567-573`). [A]

- Preflight does not check that `DESIGN_NAME` is a declared module, that the clock port exists, or that the config loads in LibreLane; and when nothing fresh is cached it runs beside the start, so the user gets a run folder and then "Stop the run?" (`setup.js:973,1013`). [A]

### 4.3 Config editing (the two-models problem)

- "Settings" (13 keys) writes the file. "All settings" (about 480 fields) is a per-run override that is never saved, pre-fills each field with LibreLane's default rather than the project's value (config says 45, field shows 50, touching it overrides the file), has no validation (lists and numbers are free text), no "modified only" filter, lists every flow's variables, and rebuilds every row on each keystroke (`config.js:467-513,610,632`). - No multi-config projects, no `meta` awareness, no flow-specific variable list. [A]
- A one-click fix defaults to "this run only" whenever the user has touched any Setup field, so the next plain Run brings the same error back (`branch.py:191,425`). [A]

- Container Step-by-step starts one container per step (about 70 cold starts), holds the single run slot while paused, and resumes each step without `-i` (`runner.py:1303-1379`). [A][?]

- Log: every line kept in memory forever, the filter rescans all of them per keystroke, no wrap, no level filter, no download (`logview.js`). [A]
- Runs started in a terminal appear only after they finish. [A][?]

- The Console's allow-list is described as keeping the server from being "a remote-code path"; it allows openroad, yosys, magic and klayout, which all run arbitrary scripts. The real boundary is the Origin check (hence G20, G21). Fix the claim. [A]
- A 404 on `/api/run-reproduce` right after a run ends. [L]

### 4.6 Failures and the fix loop

Good: the design (problem card, diff, Undo, resume from the earliest stage that
reads the setting), timing diagnosis, DRC grouping.

- **Only four halting error codes are explained** (GPL-0301, DPL-0036, GRT-0116, PDN-0185) plus two engine phrases (`problems.py:163`). Everything else shows the tool's raw words. By likely frequency, the gaps are:
  1. Verilator/Yosys syntax errors that halt a step
  2. a missing or misnamed source file, a glob matching nothing
  3. wrong top module name
  4. clock port not found, no clocks defined
  5. too many pins for the die (PPL-0024)
  6. impossible die or core area (IFP codes)
  7. detailed routing ending with violations (DRT)
  8. out of memory / killed (exit 137, `std::bad_alloc`)
  9. disk full
  10. container image and engine problems (pull failed, Podman socket, docker group)
  11. other PDN codes with macros (PDN-0179 is the most-reported open issue upstream)
  12. resizer (RSZ) and CTS codes; LVS as a crash rather than a mismatch
  Exact code numbers for items 5 to 7 and 11 need checking against LibreLane 3.0.4 before writing cards. [A][?]
- No generic fallback card (first ERROR line, tool, step, log link, "copy for help"). [A]
- Resume does not check that the PDK, image or LibreLane version still match the parent run (`branch.py:384-538`). [A]
- Verify's "Re-run step" ignores how the run was made (uses the current config, drops the run's overrides, hard-codes Classic), writes into the finished run in place, and parses overrides by splitting on commas, which breaks any list value (`routes.py:3372-3407`, `reverify.py`, `verify.js:945-956`). [A]
- Advice that can be wrong: antenna suggests `DIODE_ON_PORTS=in` whatever the cause; slew lowers `MAX_FANOUT_CONSTRAINT` first (`problems.py:688,696`). The mask-XOR boundary cleanup knows sky130's layer only. [A]

### 4.7 Runs and sweeps (the owner's top complaint)

What a user gets today, checked live and in code:

1. **Entry**: only the "New sweep" button on Runs. [L]
2. **Goal cards**: five. "Fastest clock" is broken (G11). "Smallest die" sweeps `FP_CORE_UTIL` even when the config uses a fixed die, where it does nothing. [L][A]
3. **Picking a setting**: a free-text box with a datalist of names. No type, default, current value, unit or allowed values. [L]
4. **Values**: a list or `start:stop:step`. No type check (`FP_CORE_UTIL=abc` starts a run that fails inside LibreLane); "35:65:x" silently becomes one text value. [A]
5. **Limits**: 3 settings, 64 runs. [A]
6. **Hidden riders**: every point also carries whatever is in the per-run override layer, and the sheet never says so. [A]
7. **Execution**: strictly one run at a time. On this PC (32 threads, 46 GB) a spm point takes 45 s and uses a fraction of the machine. [L]
8. **While it runs**: one strip, "Sweep running · run 1 of 3 · sweep-clk-10", only on the Runs tab. No list of queued points, no ETA, no elapsed time. Planned points do not exist in the table until they run. [L]
9. **A failing point**: recorded, sweep continues; a config error that will fail every point burns all of them. [A]
10. **Stop**: kills the current point and drops the rest. No pause, no "finish this point", no resume, no rerun-failed, no add-values. A server restart loses the queue and the row reads "1 of 3 runs" with no reason. [A]
11. **Results**: the parent row ("Sweep CLOCK_PERIOD 8–10", which hides that the values were 10, 9, 8), a Summary card with "best for timing", "best for area" (std-cell area, which barely moves in a utilisation sweep where the die is what shrinks) and a two-axis scatter. **There is no table of value against result and no chart of a metric against the swept value**, which is the one view a sweep exists for. Child rows follow the table's sort, not the sweep's order. [L]
12. **Compare**: "Compare these runs" sends the first six in table order. Selection is capped at six for everything, including delete, so cleaning up 30 sweep points takes five rounds. The Compare page opens on a wall of chips for every run of every design, has no delta columns, and shows power as raw watts and utilisation as a fraction. [L][A]
13. **No export** of a sweep or of the Runs table. No sweep name, note or tags. No archive (only delete). Twelve fixed metric columns. Filters reset on reload. [A]

Research says the same things from the user side: pros run 50 to 150 variations
overnight, six or so in parallel, capped by RAM not cores; they pick the first that
meets timing with no critical warnings; they want the winner to reproduce exactly;
they sweep small RTL changes and seeds as well as knobs; and a strong voice says a
sweep is no substitute for understanding the failure, so the diagnosis must stay on
screen. Beginners want to "tighten the constraint and rerun just to see how far it
goes". The redesign is in section 6.2.

## 5. What users and other tools say (research that changes the plan)

- **A usable LibreLane GUI is an open gap.** No Reddit thread discusses an OpenLane GUI at all; IIC-OSIC-TOOLS is the default "everything installed" answer; a browser RTL-to-layout tool was welcomed with "At least this one doesn't look vibe coded" and "I would prefer one that does not require signing up".
- **Install is still where people stop** (Nix builds of 4 to 5 hours, two unanswered Apple Silicon asks, a student who had an AI do the Linux setup). LanEx's installer is its strongest pitch; say "no Linux, no Nix, no PDK_ROOT" on the page.
- **Errors that don't say why** is the top upstream complaint (OpenLane issue 1574 on DPL-0036, 24 comments: "what's a core and what's not-core?"). This is exactly LanEx's failure-card idea; it needs coverage (4.6).
- **Experts use a GUI to look, not to run.** They script runs and open results. So: runs started in a terminal must show up live, every action must echo its command, and results views (timing paths on layout, congestion) matter more to them than run controls.
- **Sweeps**: 50 to 150 runs overnight, about 6 in parallel, RAM-bound; winner = WNS ≥ 0 and no critical warnings; the winner must replay exactly (ORFS AutoTuner's best config famously did not); a cheap synthesis-only exploration first is wanted, and LibreLane ships one (`SynthesisExploration`: nine strategies through pre-PnR timing, prints a table, picks nothing, crashes if all fail).
- **Patterns worth copying**: Vivado's Design Runs (parent/child rows, out-of-date, make active); Quartus DSE II's point states (Not submitted / Waiting / Running / Successful / Error), cap on parallel compiles and results-retention choice (all / best / reports only); W&B's group-by any config key, parallel coordinates and run diff; MLflow's side-by-side compare that highlights differences; VS Code's settings search with a "modified" filter and a raw-file toggle.
- **Do not build**: auto-generated constraints (experts reject it outright), black-box "AI optimiser" claims, anything that hides the plain config file, a sign-up wall.
- **LibreLane facts for the run engine** (from its source): there is no built-in sweep; a sweep is N invocations with `-c` overrides and distinct `--run-tag`s. `--from/--to/--only/--skip` work on sequential flows only. A run can be forked from another's state with `-i <state_out.json> --from <step>`, so points that share synthesis can share it. Concurrency is the caller's job; set `-j` per run so the sum fits the cores.

## 6. Three designs that fix most of the list

### 6.1 One settings model

The config file is the truth. Replace "Settings" and "All settings" with one
**Configuration** editor:

- Every row shows the effective value and where it comes from: LibreLane default, PDK, `config.yaml` line N, a `pdk::sky130*` section, or a this-run override.
- Editing writes the file (YAML line edit as today, with diff and Undo). A per-row switch makes it "this run only", and such rows are shown as chips next to the Run button ("2 one-off settings") so they are never invisible. They are stored per project and cleared after the run unless pinned.
- "For this PDK only" writes the matching `pdk::` section (wire `scope` through `/api/config/set`).
- Typed inputs from LibreLane's own variable types (numbers with units, enums, list editor, file picker); validation by LibreLane's config loader before the run, shown on the row.
- Views: Common (today's 13, first for beginners), Modified, In file, By stage, Search (including deprecated OpenLane names). Only the chosen flow's variables.
- A raw-file toggle, VS Code style.
- A config chooser when a project has several configs; `meta.flow` shown and used.

This removes G13, most of 4.3, the hidden sweep riders, the fix-loop save confusion
and the false copy.

### 6.2 Jobs and Studies (the sweep redesign)

**Job queue**, persisted in the project (`.lanex/queue.json`), survives a restart:

- A job is a run spec (config, overrides, flow, range, PDK). "Run" while busy offers "Add to queue".
- `max_parallel`, default from memory (free RAM divided by this design's past peak, shown as "2 at a time, 46 GB free"), each run given `-j` so the total fits.
- A queue chip in the top bar on every page: "Running 2 · 5 queued · about 1 h 20 left", with a popover to reorder, remove, pause, or stop after the current run.
- On startup: mark interrupted jobs, find orphan containers, offer Continue or Stop.

**Study** (the user-facing word can stay "sweep"): name, base, axes, method, goal, stop
rule, planned points with a state each (queued, running at stage k, passed, failed
with reason, skipped, pruned).

- **New study sheet, simple mode** ("Try variations"): goal cards that work. Fastest clock = periods from the project's clock downward, run all, headline "fastest that met timing: 8 ns (125 MHz)". Smallest chip = drives the variable that actually sizes the die. Synthesis strategies = LibreLane's own `SynthesisExploration` first (minutes, not full runs), then full runs of the top few. Picking a setting shows its description, unit, default and current value; values as chips or min/max/step with a live "6 runs, about 5 min, 2 at a time, 0.9 GB".
- **Advanced mode**: any variable; list, range, N points, log; grid or paired; Verilog parameters and defines as axes; constraints (timing met, DRC clean); stop rules (none, first pass, first failure, stop when two points fail the same way early); a preview table of planned points with a tick to drop any; results retention (keep everything / keep GDS of passing points / metrics only); "share synthesis" when no axis touches it.
- **Study view**: a table with the swept values first, sorted by value, then state, stage, reason and metrics; a line chart of any metric against the swept value (one axis), a heatmap (two), a Pareto scatter of any two metrics with the front marked; "best so far" by the goal. Actions: Resume, Rerun failed, Add values, Stop after this point, Compare all, Export CSV/JSON, and "Use these settings" (writes base plus point as a reviewable diff with Undo).
- The timing or congestion diagnosis of the run the study was started from stays pinned at the top: a sweep is a tool, not a substitute for the cause.

**Runs table**: no six-run cap except on Compare; select-all and select-a-study;
bulk archive, delete, tag, export; add any metric or config variable as a column;
filters and named views persisted; "terminal" origin for runs LanEx did not start,
followed live from their `flow.log`.

**Compare**: the selection comes from Runs (no chip wall); a reference column with Δ
and Δ% per run; one formatter; "only what differs"; config diff without path noise;
layout thumbnails side by side; up to about 12 runs.

### 6.3 The run menu

Three plain sections, each mapping to a LibreLane flag and shown as the live command
line underneath:

- **What**: flow (from the config, changeable); whole flow / up to a stage / from a stage / only one step / skip steps.
- **How**: engine; threads auto or N; low priority; keep the PC awake (on by default).
- **When**: run now or add to queue; tell me when it finishes (on by default).

## 10. UI and experience: findings and direction (added 2026-11-15)

The first pass looked at every tab once, at 1600×900, dark theme, default states. That
is enough to see the pattern and not enough to redesign from. The redesign session
starts with a complete visual audit (every tab, sub-tab, sheet, dialog and state at
1366, 1920 and 2560 px, dark and light).

### 10.1 Why it feels cluttered

The UI is additive. Each tab was rebuilt in its own session with the brief "make it
look the best and explain itself", so each grew its own hero, its own explainer, its
own filters and its own stat tiles. Nobody subtracted across the whole app.
`PRODUCT.md` principle 4 says "chrome recedes, the design leads"; the screens do the
opposite.

- **Status shown as a headline, repeatedly.** The same "Clean" verdict hero on Flow, in the Runs row, on Analytics and on Verify; a "Ready to run" hero on Tools; a marketing hero on Setup that stays above the open project.
- **Permanent teaching text.** Every page opens with an eyebrow, a large heading and a two-to-three-line paragraph ("One row per run. Click a row to…"), about 150 px on every visit.
- **Stacked decoration.** Blueprint grid background, corner brackets, glowing card edges, a rainbow hairline under the top bar, letter-spaced uppercase mono labels on nearly everything.
- **Graphics that carry no information.** 23 green squares on Verify, 17 on Tools.
- **Too many controls visible at once.** Layout shows about 25 (two separate 3D buttons, four side tabs, three presets, nine toolbar icons, a hint bar, a caption). Runs has a scope toggle, search, five status chips, four origin chips, a column chooser and fourteen columns. Cells has five stat tiles, twelve filter chips, two checkboxes and a sort before the list, then six more tiles in the detail.
- **An icon beside every number.** The provenance magnifier appears about 20 times per Analytics or Verify screen.
- **Tabs inside tabs.** Nine rail tabs, then Setup 6, Analytics 9, Verify 7, Layout 4, Cells 3: close to 38 places. Analytics and Verify present the same checks twice.
- **Rare controls in permanent chrome.** Zoom −/100 %/+ and theme in the top bar; both Console and Logs in the status bar; a "RUN / COMPARED WITH" selector pair repeated at the top of each results page.
- **No scale underneath.** 35 font sizes, 13 corner radii, about 30 breakpoint widths, 222 hard-coded colours, four overlay implementations.

### 10.2 Principles for the redesign

1. **The design leads.** The user's chip, run and numbers take the screen; the frame is quiet.
2. **One page, one job, one primary action.** Everything else is secondary or one click away.
3. **Status is small, problems are big.** A clean run is one line. A failed run gets the card, the reason and the fix.
4. **Teach at the moment of need.** Empty states, hover, the failure card, help. Never in permanent chrome.
5. **Two levels at most.** The answer first; the raw truth (file, step, command) one click away.
6. **Numbers are the interface.** Tabular mono numerals, muted units, aligned columns; a table or a line, not a card per number. Where a number comes from is shown on click, not by an icon next to each.
7. **One scale.** About five text sizes, a 4 px spacing step, two radii, one border weight; depth by tone, not glow.
8. **Colour means something.** One accent for action; green, amber and red for verdicts only; layer colours only inside the layout.
9. **Keep the identity, drop the ornament.** Dark, technical, the LanEx mark, Barlow and JetBrains Mono stay. The grid texture, brackets, glows and decorative bars go.
10. **Built for keyboards and every screen.** Focus order, one overlay behaviour, correct at 1280 px, crisp at 4K, dark and light equal.

### 10.3 Starting direction (the redesign session owns the final call)

- **Frame.** Rail down to the places people work in (Project, Code, Run, Runs, Results, Layout, Library), with Tools as a system entry at the foot. Top bar: project, the run in view (one shared control instead of a selector on each page), search, Run. Zoom, theme, help and preferences in one menu. One status line: run state, queue, problem count, Console. The "not a sign-off tool" notice stays visible on Results and in About.
- **Project (today's Setup).** With no project: three actions and the recent list, nothing else. With a project: its facts (top module, clock, PDK) as one compact editable summary, sources, readiness and Run on one screen at 1366×768. Configuration is its own page (section 6.1).
- **Run (Flow).** Already the best page; keep its structure. A clean result collapses to a strip so the stages and log get the room.
- **Runs.** A one-line header, one toolbar row, the table at full height. Details in a side panel instead of expanding rows. Studies as groups (section 6.2).
- **Results.** Analytics and Verify merged: a verdict line and the key numbers, then Timing, Physical checks, Area and power, Routing, All metrics. Compare is a mode of this page, not a tab.
- **Layout.** The canvas edge to edge. One collapsible layers panel, one toolbar, one "Open in" menu, a slim stage strip. No duplicated controls.
- **Library (Cells and macros).** A list and a detail. Counts become one summary line; filters become one control.
- **Tools.** A status list. A headline only when something needs fixing.
- **IDE, wizard, guide, palette, Console, sheets, dialogs.** Same tokens, one sheet pattern, one dialog pattern.
